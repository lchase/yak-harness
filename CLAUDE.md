# CLAUDE.md — yak-harness

`yak-harness` is a **stateless cron reconciler** that sits between a
GitHub Issues backlog and [yak](https://github.com/lchase/yak). The full
design is [`docs/spec.md`](docs/spec.md); the decision trail is
[`docs/design/`](docs/design/). Read the spec before making non-trivial
changes. This file records the invariants that must not be broken.

## What the harness is

Each run ("tick") it: wakes, reads desired state (qualifying issues +
their status labels) and observed state (yak runs on disk, PRs on
GitHub), computes the diff, applies **one step** toward closing it, and
exits. No daemon; nothing runs between ticks.

Two jobs: (1) manage a GitHub Issues backlog by label — launch a
`yak run` per qualifying issue and drive a status-label state machine;
(2) bridge yak's gate protocol — post the rendered prompt as an issue
comment, parse a human's reply into a schema-valid answer, resume the
run.

## Core invariants

1. **yak's engine stays entirely ignorant that GitHub exists.** Drive
   yak only through its documented CLI (`yak run`, `yak resume`,
   `yak pending`) and its on-disk journal / `pending/` contract. Never
   patch yak, never assume `yak run --id` or `yak cancel` (spec §11,
   §12).

2. **No `@lchase/yak` build dependency.** yak is a *runtime* requirement
   (the `yak` binary on `PATH`). The three on-disk yak shapes the
   harness reads — `GatePendingRequest`, the `run.started` /
   `run.finished` journal events, and `StepFailure`
   `{reason, detail, recoverable}` — are re-declared as local `zod`
   schemas and used to validate at the boundary (spec §10.1).

3. **Durable state lives in exactly two places, neither the harness:**
   GitHub (issue labels + hidden marker comments) and yak's `.runs/`
   journal (authoritative for run status). `.harness/` holds only
   non-load-bearing operational scratch (lock file, per-run pid files);
   deleting any of it between ticks must not lose correctness — a full
   rescan reconstructs the truth (spec §2).

4. **The tick is `observe → plan → apply`.** `observe` does all reads;
   `plan` is a **pure function** of the `Observation` — no I/O, no
   mocks needed to test; `apply` does all GitHub / yak side effects
   (spec §6.1). Keep label strings out of the tick code — they come
   from the §8.2 transition table called as a pure function.

5. **Every `apply` action is idempotent** and guarded by a predicate
   evaluated in `plan` from the `Observation`. A tick may die at any
   point; re-attempting any action must be safe (spec §6.4).

6. **At most one `yak run` launch per tick**, even when several
   concurrency slots are free. This keeps the snapshot-and-diff of
   `.runs/` unambiguous (spec §5.1, §6.3). An idle harness ramps to
   `maxConcurrent` over several ticks.

7. **Run ↔ issue linkage lives in the tracker only**, as one marker
   comment per launch:
   `<!-- yak-harness run=<id> branch=<branch> launched=<ts> -->`.
   Reconstructed from scratch every tick. Last marker wins; earlier
   markers are kept as history and their **count is the attempt
   counter** (spec §5.2, §9.2).

8. **The harness transitions labels only on evidence from yak's journal
   / on-disk state, never on a timer alone.** `stalled` is itself a
   journal-mtime fact (last-event mtime older than
   `stalledAfterMinutes`), computed as a pure function of the journal —
   no harness clock or counter (spec §6.2, §8.2).

9. **`yak:failed` is a trap.** The harness never auto-leaves it. It
   also never auto-relaunches off a marker alone, and never guesses an
   issue for an orphan run (spec §5.5, §8.2).

10. **The harness performs zero destructive cleanup.** Does not close
    issues, delete branches, touch `.runs/` dirs or worktrees, or
    delete / strike through its marker comments (spec §8.4).

## Label state machine (spec §8)

One harness-owned, single-valued `yak:<status>` label is the whole
machine. Exactly one `yak:<status>` per issue — two is a harness fault
(flag, act on nothing).

| status | meaning |
|---|---|
| `yak` only (no `yak:<status>`) | qualified by a human, not yet launched |
| `yak:running` | run launched, `alive` |
| `yak:waiting` | suspended on a gate — human reply needed |
| `yak:pr-open` | run finished ok, PR opened |
| `yak:failed` | failed / stalled / orphan / stale — needs human (trap) |
| `yak:done` | PR merged — terminal, inert |

Human-owned: **`yak`** (`qualifyingLabel`, the scope defence — a human
only applies it to already-scoped work; stays on for the whole
lifecycle); **`yak:hold`** (park override — harness skips the issue
entirely; does not pause a live `yak run`).

## Gate bridge (spec §7)

- The `rendered` string is freeform prose the harness has **no semantic
  understanding of** — post it verbatim.
- The contract shown to the human is **generated by walking
  `answerSchema`'s properties**, not hand-authored per gate kind.
- **Spec constraint on yak workflow authors:** gates meant to be
  harness-bridged must keep `answerSchema` a **flat object of scalar /
  enum properties**. Nested objects / arrays → the harness routes the
  issue to `yak:failed` and stops.
- **No LLM** in reply parsing. Line-based `key: value`. Author filter:
  `author_association` ∈ {`OWNER`, `MEMBER`, `COLLABORATOR`}, read off
  the comments payload.
- Validate the parsed answer against `answerSchema` with `ajv` **before**
  `writeAnswer`.
- **One** re-prompt on a malformed reply; a second bad attempt →
  `yak:failed`. A never-answered gate has **no timeout** — it sits in
  `yak:waiting` and holds its cap slot; that visible stall is the
  signal.

## Failure / retry (spec §9)

- Retry **iff** `terminalFailure.recoverable === true` **and**
  `attemptCount < 2`. Hard cap 2 attempts total. A retry is a **fresh
  `yak run`** (new id, new marker), never `yak resume`.
- No explicit back-off — the cron interval is the spacing.
- `stalled` runs: the harness kills the detached pid it recorded in
  `.harness/runs/<id>.json` (verify pid is alive **and** a `yak`
  process — guard pid reuse), then relabels `yak:failed`. `stalled`
  **never retries**.
- On every transition into `yak:failed`, post **one** comment guarded
  by a `<!-- yak-failed run=<id> -->` marker.

## Configuration (spec §4)

One plain-JSON file, path passed as `--config <path>` to every
invocation, `zod`-parsed at startup before any observation. Required:
`repo`, `yakRepoPath`, `stalledAfterMinutes` (**no default** — operator
must set it). Defaults: `qualifyingLabel` `"yak"`, `maxConcurrent` `2`,
`workflow` `"implement-change"` (spec §4.1 — one workflow spanning
bug / feature / chore; `design`/`design-review`/`docs` self-skip via
`skipIf` off the `assess` step; the `deliver` loop bridges review
findings back to `build`, bounded, then suspends).

**Locked constants** are `const` in source, not config — each carries a
`// config candidate if a real need appears` comment: gate re-prompt
limit `1`, max run attempts `2`, accepted `author_association` set, the
`yak:` status prefix + six status names, `.harness/` location, all
marker-comment formats.

The **cron interval is not harness config** — it lives only in the
crontab line. The tick is stateless and idempotent; it does not know
its own cadence.

## Toolchain

TypeScript, ESM, Node 22, `tsup` build to `dist/`, `vitest`. `bin`
entry `yak-harness`. Runtime deps: `zod`, `ajv` only. Conventional
commits. Published to npm as **`@lchase/yak-harness`** via
`release-please` + OIDC trusted publishing (`.github/workflows/release-please.yml`
opens the release PR and dispatches `publish.yml`). `CHANGELOG.md` is
**release-please-generated from v0.1.0 on — never hand-edit it**; the
`## Pre-0.1.0 development` section is frozen history. The box can still
run from a source checkout (`git pull && npm run build`) instead of the
published package.

## Commands

- `npm run build` — `tsup` to `dist/`
- `npm test` — `vitest run`
- `npm run typecheck` — `tsc --noEmit`

## Implementation order (spec §13)

1. Config schema + `doctor` + the three re-declared yak on-disk zod schemas.
2. `observe` — the read phase, against fixture `.runs/` trees and canned `gh` JSON.
3. `plan` + the §8.2 transition table — pure, exhaustively unit-tested.
4. `apply` for C and D (relabel + launch) — end-to-end to `yak:pr-open`.
5. `apply` for E (orphan/stale) and §9 (retry, stalled kill).
6. The gate bridge (§7) — A and B. `docs/design/` prototype is the acceptance reference.
7. `tick.log`, `--dry-run`, the lock file, packaging.
